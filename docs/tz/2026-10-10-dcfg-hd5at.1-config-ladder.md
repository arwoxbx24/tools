## U1. Что сделать
1. Конфиг читать `jq` (уже зависимость скрипта). Путь: `${CODE_CHANNEL_CONFIG:-<корень tools>/config/code-channel.json}`, корень — от каталога скрипта. Нет файла или `jq` упал → stderr `code-channel: конфиг <путь> не читается`, exit 3.
2. Форма = id записи `ladder[]` (`go`, `codex`, `openrouter`, `bitrixgpt`, `kimi`) или алиас: `1`→bitrixgpt, `2`→codex, `3`→openrouter. `auto`/`audit` идут по включённым записям в порядке массива.
3. Явный вызов id с `enabled:false` → stderr `code-channel: провайдер <id> выключен в конфиге`, exit 3, исполнитель не запускается.
4. `run_form` получает id; поля `model`, `key`, `secret`, `base` — из записи. Ветки по номерам форм (`codex`-исполнитель, проверка `/key` и `usage_daily` openrouter, проба и файл `bitrixgpt.block`) — по id.
5. Запись без `key`: без загрузки секрета, без HTTP-прекверки, без проверки белого списка `opencode.jsonc`; модель проверяется только префиксом `<что-то>/`. Особый случай `opencode-go/*` (v3 dcfg-4ua5b) удалить — он становится общим правилом.
6. Сверка провайдера (`reconcile`): ожидаемый providerID = часть `model` до первого `/` (`opencode-go`, `openrouter`, `bitrixgpt`, `kimi-for-coding`). Для codex — как сейчас.
7. Лестница (KTD6): отказ провайдера и rc 0 без изменений → строка `switch <id>→<id>` и следующая включённая запись. Сразу выход: 3, 5, 15, 22, 24. Последняя включённая запись возвращает свой rc, а при rc 0 без изменений — 16. Ничего не привязано к id `codex`.
8. `--model <m>` (KTD7): только при явном id; правила проверки — записи этого id. С `auto`/`audit` → exit 3.
9. `code-channel --plan` (без других аргументов): по строке на включённую запись в порядке массива: `<id> <model|-> <effort|->`, rc 0, без сети и исполнителей.
10. stderr-метки `form=<n>` → `form=<id>`; «форма N …» → «форма <id> …».
