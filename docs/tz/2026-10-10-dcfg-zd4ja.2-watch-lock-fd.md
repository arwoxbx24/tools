# ТЗ dcfg-zd4ja.2 — ship-post --watch: потомки не держат watch.lock

## U1 Причина (факт)
`bin/ship-post:537` открывает замок `exec {watcher_lock}>"$SHIP_POST_STATE_DIR/watch.lock"` и берёт `flock -n`.
Все потомки наследуют этот fd: воркер репозитория (`( ... ) &`, строки 556–584), его доставки (`( ... ) &`, строка 494) и `coproc JOURNAL` (строка 587).
Замер на живом процессе: 40 потомков, у каждого 1 fd на watch.lock.
pm2 watch шлёт SIGINT, родитель умирает, фоновые доставки переживают его и держат замок.
Новый экземпляр падает `ship-post: watcher already active` (rc 1), pm2 перезапускает в цикле, pm2-loop-guard останавливает сервис (10.10, 19:50–19:51).

## U2 Правка (только эти 2 файла)
1. `bin/ship-post`, `do_watch`:
   - первой командой внутри подоболочки воркера (строка 556, `(` перед `local pending ...`) добавить `exec {watcher_lock}>&-`;
   - внутри `coproc JOURNAL { ... }` перед `cd` добавить `exec {watcher_lock}>&-;`.
   Ничего больше в `bin/ship-post` не менять. Родитель держит замок как раньше: защита от двух watcher-ов сохраняется.
2. `bin/ship-post-test`: новая функция `test_watch_lock_released` и её вызов рядом с `test_concurrent_repositories`. Схема:
   - `setup_submit lockrel codex/dcfg-lockrel.1; commit_candidate dcfg-lockrel.1; : > "$d/events"`;
   - запустить в фоне watcher A: `( export BEADS_ACTOR=Codex BD_STATUS=closed BD_ASSIGNEE=Codex MOCK_SHIP_DELAY=6 TEST_TIMEOUT=12; run_tool "$d" --watch ) >"$d/a.log" 2>&1 &`;
   - ждать до 5 с (цикл `sleep 0.2`), пока `$d/ship.calls` не станет непустым: доставка идёт;
   - найти главный процесс A: прямой потомок процесса `timeout`, чья командная строка содержит `$d/bin/ship-post --watch` (через `pgrep`);
   - смоделировать pm2: `kill -TERM <main>`, через 1 с `kill -KILL <main>` (если ещё жив);
   - сразу запустить watcher B: `out=$(export BEADS_ACTOR=Codex BD_STATUS=closed BD_ASSIGNEE=Codex TEST_TIMEOUT=2; run_tool "$d" --watch 2>&1)`;
   - проверка: `[[ $out != *'watcher already active'* ]] && pass watch_lock_released || fail watch_lock_released "$out"`;
   - дождаться фонового A (`wait`), чтобы тест не оставлял процессов.

## U3 Критерий (одна команда)
`bash bin/ship-post-test 2>&1 | grep -E '^(FAIL|PASS watch_lock_released)|checks'`
- до правки `bin/ship-post` (только тест): `FAIL watch_lock_released`. Сначала добавь тест и убедись в этом;
- после правки: `PASS watch_lock_released` и 0 строк `FAIL`.

## Факт после прогона 1
Прогон 1 ушёл в эксперименты с сигналами в `/tmp/opencode` (`chmod +x` отказан правами) и не сделал ни одной правки. Эксперименты не нужны: механизм уже доказан.
Делай строго по шагам, без скриптов в /tmp и без `chmod`:
1. В `bin/ship-post-test` перед строкой `test_service_recovery(){` вставь функцию дословно:
```bash
test_watch_lock_released(){
 local out t m a i
 setup_submit lockrel codex/dcfg-lockrel.1; commit_candidate dcfg-lockrel.1; : > "$d/events"
 ( export BEADS_ACTOR=Codex BD_STATUS=closed BD_ASSIGNEE=Codex MOCK_SHIP_DELAY=6 TEST_TIMEOUT=12; run_tool "$d" --watch ) >"$d/a.log" 2>&1 & a=$!
 for i in $(seq 1 50); do [[ -s $d/ship.calls ]] && break; sleep 0.2; done
 t=$(pgrep -n -f "^timeout .*$d/bin/ship-post --watch"); m=$(pgrep -P "$t")
 kill -TERM "$m"; sleep 1; kill -KILL "$m" 2>/dev/null
 out=$(export BEADS_ACTOR=Codex BD_STATUS=closed BD_ASSIGNEE=Codex TEST_TIMEOUT=2; run_tool "$d" --watch 2>&1)
 [[ -n $m && $out != *'watcher already active'* ]] && pass watch_lock_released || fail watch_lock_released "m=$m $out"
 wait "$a"
}

```

В том же файле: в блок выбора групп перед веткой `elif [[ ${SHIP_POST_TEST_GROUP:-all} == adr35 ]]; then` добавь ветку `elif [[ ${SHIP_POST_TEST_GROUP:-all} == lock ]]; then` с телом `test_watch_lock_released`. В общем списке (ветка `else`) после `test_concurrent_repositories;` добавь `test_watch_lock_released;`.
3. Прогон: `SHIP_POST_TEST_GROUP=lock bash bin/ship-post-test`. Ожидание на старом коде: `FAIL watch_lock_released ... watcher already active`. Главный агент это уже наблюдал.
4. В `bin/ship-post`, `do_watch`: строку `   local pending atoms atom failed` (подоболочка воркера) предвари строкой `   exec {watcher_lock}>&-`. ## Факт после прогона 2 (ошибка ТЗ, не исполнителя)
Правка `bin/ship-post` (2 строки) в worktree уже верна, не трогай её.
Тест убивал не тот процесс: `do_watch() (` (bin/ship-post:531) — подоболочка, ребёнок верхнего процесса; именно она держит замок. После `kill` верхнего она осталась с ppid=1 — поэтому FAIL при любом фиксе.
pm2 реально шлёт сигнал всему дереву; do_watch ловит его (`trap 'exit 143'`), cleanup ждёт воркеров (они выходят за ~1 с по файлу stop), а фоновые доставки (`scan_repo` их не ждёт) живут дальше.
Единственная правка теста — в `test_watch_lock_released` заменить строку
`kill -TERM "$m"; sleep 1; kill -KILL "$m" 2>/dev/null`
на две строки:
```bash
 w=$(pgrep -o -P "$m"); kill -TERM "$w" "$m"
 for i in $(seq 1 25); do kill -0 "$w" 2>/dev/null || break; sleep 0.2; done
```
и добавить `w` в `local`. Остальное не менять.
Проверка:
1. `git stash push bin/ship-post` → `SHIP_POST_TEST_GROUP=lock bash bin/ship-post-test` → ожидание `FAIL watch_lock_released ... watcher already active` (замок держит доставка с MOCK_SHIP_DELAY=6) → `git stash pop`.
2. `SHIP_POST_TEST_GROUP=lock bash bin/ship-post-test` → `PASS watch_lock_released`.
3. Полный `bash bin/ship-post-test 2>&1 | tail -3` → `failures=0`.
Вывод 1–3 дословно в отчёт. Без диагностических скриптов в /tmp.
