# ТЗ dcfg-8yqv4.14 — ship-post: конечные состояния dev-delivered / wait-owner / prod-hold; без исключений; без повторов

## U1 — курьер понимает ответы ship v4
Разведка — repowise; индекс: repowise/CBM проверен, нет — `tools/bin/code-memory-enable`.

Причина (spec:099 v4, ADR-15, ADR-18, FR-030, FR-031). После dcfg-8yqv4.12 ship отвечает rc 0 и строкой в выводе в двух новых случаях:
- `prod:wait-owner no-ci`: ветка запушена, PR открыт, merge нет;
- `prod:hold guarded <причина>`: только локальный коммит.

Сейчас `bin/ship-post` с этим не справляется:
- `--submit` отказывает репо с `ga_skip_reason` (`repository excluded from courier`, около `:131`);
- скан для репо без CI вообще не вызывает ship (`write_wait_owner_no_ci_receipt`, около `:317-327` и `:402-408`), поэтому PR не появляется;
- после ship rc 0 `remote_result` ждёт слитый PR. Открытый PR даёт `record_failure 23`, и атом уходит в повтор.

Решение (ADR), правка только `bin/ship-post` и `bin/ship-post-test`:
1. `--submit`: отказ по `ga_skip_reason` удалить. Репо из `ga_roots` с причиной принимается так же, как прочие.
2. Скан: специальный путь no-ci (`! repo_has_pr_ci` → квитанция без вызова ship) удалить. Атом любого репо идёт в ship. Функцию `repo_has_pr_ci` удалить, если вызовов не осталось.
3. После ship rc 0 и до `remote_result` смотреть вывод ship в `$rf.log` (последний запуск):
   - есть `prod:wait-owner` → квитанция `stage:"wait-owner"` с номером PR из строки `pr:<n>` и `bd_cmd update "$atom" --append-notes "ship-post: wait-owner — PR открыт, на прод только ship-promote по слову владельца"`; `rm -f -- "$inflight"`; return 0;
   - есть `prod:hold` → то же со `stage:"prod-hold"` и заметкой `ship-post: prod-hold guarded — защищённое репо, на прод только словом владельца по закону`.

   Повторно скан такие атомы не берёт: финальны только `.stage` = `wait-owner` и `prod-hold`. Старая стадия `wait-owner no-ci` (из dcfg-ta2r0: ship не вызывался, PR нет) НЕ финальна. Скан один раз прогоняет такой атом через ship, получает PR и перезаписывает квитанцию на `wait-owner`. Это 4 атома arwox-v3-src: dcfg-jkd6x, dcfg-wowp4.2, dcfg-3v3z1, dcfg-n575n. Без PR их нечем перенести (`ship-promote` для plain ищет открытый PR атома). Тест: квитанция `wait-owner no-ci` → скан вызывает ship ровно один раз → квитанция `wait-owner` с номером PR → второй скан ship не вызывает.
4. Конечные коды. ship rc 10, 50 или 80 → `record_failure` один раз, атом больше не берётся до новой сдачи. Временным (повтор) остаётся только 70 по существующему grep сетевых строк. Логику `dcfg-m2lzu` (30 при открытом PR не превращается в 70) не возвращать.
5. `ship`, `ship-promote`, `git-sync`, `git-auto-lib` не менять.

Тест — `bin/ship-post-test`, номера ≥140. Mock ship печатает нужную строку и выходит с нужным кодом:
- репо с `ga_skip_reason` (`stroyremont`) → `--submit` rc 0; скан вызывает ship; вывод `prod:hold` → квитанция `prod-hold`; второй скан ship не вызывает;
- репо без workflow → скан вызывает ship; `prod:wait-owner no-ci` и `pr:7` → квитанция `wait-owner` с PR 7; заметка в bd; второй скан ship не вызывает;
- ship rc 50 → одна запись сбоя; второй скан ship не вызывает;
- ship rc 70 → повтор разрешён (как сейчас).

Тесты N2 и N3 атома dcfg-ta2r0 привести к новому поведению: это прямое требование spec:099 v4, а не ослабление. Прочие проверки не ослаблять.

Дока: обновить в `docs/ship-post-ARCHITECTURE.md` разделы о состояниях и отказах: `wait-owner`, `prod-hold`, конечные коды. Иначе CI-гейт `ship-doc-check` отклонит PR.

Запреты: только `bin/ship-post`, `bin/ship-post-test`, `docs/ship-post-ARCHITECTURE.md` и этот ТЗ. Без `--force`, `reset --hard`, `rm -rf` вне `/tmp`. Принципы: KISS, YAGNI, fail fast.

## Уточнение 1 — исправление поверх отправленного SHA не застревает (главный агент, 09.10)
Причина (замер, атомы dcfg-8rtt0 и dcfg-dtl8p): CI отклонил доставку → агент кладёт исправление новым коммитом поверх отправленного → `deliver_one` видит `inflight` с другим SHA → `record_failure 24`, доставку пришлось толкать вручную.

Решение (ADR, только `bin/ship-post`): в `deliver_one` в проверке `[[ -f $inflight && $(cat "$inflight") != "$head" ]]` перед `record_failure 24` — если `git -C "$wt" merge-base --is-ancestor "$(cat "$inflight")" "$head"` (старый SHA — предок нового) и удалённый PR не слит (уже доказано: `rc` 21 или 22 выше), то это продолжение той же доставки: строка в `$rf.log` `superseded <old> -> <new>`, перезаписать `inflight` новым SHA и идти дальше в ship. Не предок → код 24, как сейчас.

Тест (номер ≥140): `inflight` = A, новая сдача B, A — предок B, PR не слит → ship вызывается с `--expected-head B`, кода 24 нет; `inflight` = A, B не потомок A → код 24.
