# ТЗ dcfg-8yqv4.27 — параллельная доставка атомов репо, слияние по одному на свежей основе (spec:099 v6 ADR-30, ADR-31)

## U17
Разведка — ПЕРВЫМ repowise, точными именами: `/root/.local/bin/repowise context bin/ship-post::scan_repo bin/ship-post::deliver_one bin/git-auto-lib::ga_ci_wait bin/git-auto-lib::ga_lock --path /root/workspaces/tools --include callers`. Затем `bin/ship` строки 103–125 (`locked_core`, `ga_lock … locked_core`) и 180–200 (CI, merge).

Замер (главный агент, 10.10):
- `bin/ship-post:scan_repo` — `deliver_one` атомов одного репо вызывается по одному (строка с `deliver_one "$wt" "$atom" "$tz" "$head" "$repo" "$branch"`) под `flock -x` репо. N атомов = N × ~4 мин CI.
- `bin/ship` уже защищён: `ga_lock "$name" 60 locked_core` (push), `ga_lock "$name" 60` перед `gh pr merge --merge --match-head-commit`. Ожидание CI (`ga_ci_wait pr …`) без замка.
- Риск (ADR-31): при параллели CI атома B прошёл на старом `origin/<base>`; после слияния A слияние B без перепроверки может сломать main. GitHub: «By default, a workflow only runs when a pull_request event's activity type is opened, synchronize, or reopened.» и «GITHUB_SHA for this event is the last merge commit of the pull request merge branch.» (docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). Workflow tools: `pull_request` без `types`.

Правки:
1. `bin/ship-post:scan_repo`: вызов `deliver_one` — в фоне (`&`), не более `SHIP_POST_JOBS` (по умолчанию 8) одновременно; после цикла дождаться всех и посчитать `ok`/`failed` по коду каждого PID (`wait "$pid"`). `flock` репо держать до конца ожидания (второй проход не берёт те же атомы). Остальная логика цикла без изменений.
2. `bin/ship` `locked_core`: после успешного `g fetch -q origin "$base"` запомнить `ci_base=$(g rev-parse origin/$base)` (глобально для дальнейших шагов).
3. `bin/ship` перед `gh pr merge` под `ga_lock "$name" 60`: `g fetch -q origin "$base"` (ошибка → 70); если `origin/$base` ≠ `ci_base` — НЕ сливать: снять замок, `gh pr close` + `gh pr reopen` (ошибка gh → 70), `ci_base=<новый origin/$base>`, `since=<время до reopen, ISO>`, снова `ga_ci_wait pr "$slug" "$num" "<head>" "$since"` (40/30 как сейчас), затем снова шаг 3. Не более 5 кругов, иначе `leave 70 base-moving`. Совпало → слияние как сейчас. Печатать `ship: base moved <old>..<new>, re-CI #<num> round <k>`.
4. `bin/git-auto-lib:ga_ci_wait` `pr`: необязательный 5-й аргумент `since`; при нём фаза появления ждёт прогон с `createdAt >= since` (`gh run list … --json status,createdAt` + `jq`), старый зелёный прогон того же SHA не засчитывается. Без `since` — поведение прежнее.
5. `bin/ship-post:do_submit`, строка `ship-post: fix: …` при коде 50: команда слияния должна давать коммит с трейлерами, иначе повторная сдача отклоняется (`nothing to commit and HEAD trailers do not match` — замер 10.10 на .23). Текст: `git -C <wt> fetch origin && git -C <wt> merge origin/<base> -m "<atom>: merge origin/<base>" -m "ТЗ: <ТЗ из трейлера HEAD>" -m "Atom: <atom>" -m "Agent: <agent>"; resolve files; git -C <wt> commit --no-edit; test; submit again`. Значения подставить из текущего HEAD.
6. `docs/ship-post-ARCHITECTURE.md`: §3 п.4 — одна строка «атомы репо доставляются параллельно (до `SHIP_POST_JOBS`), merge по одному под `ga_lock`, при сдвиге основы — повторный CI (ADR-30/31)»; §8 — `SHIP_POST_JOBS`.

`bin/ship-post-test`: группа `SHIP_POST_TEST_GROUP=adr30`: три атома одного репо, заглушка `ship` с `sleep 2` → проход `scan_repo` < 5 с, `ok=3`. `bin/ship-test`: тест группы для п.3 (заглушка `gh`: основа сдвинулась после CI → вызваны `pr close`+`pr reopen`, `pr merge` только после второго CI; основа не сдвинулась → merge сразу) — если в `ship-test` есть механизм групп, использовать его; иначе отдельная функция, запускаемая переменной `SHIP_TEST_GROUP=adr31`.
